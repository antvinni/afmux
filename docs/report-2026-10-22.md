# afmux: can Apple's on-device model save a coding agent tokens?

Report on one day of building and measuring, 2026-10-22.

## Verdict

No. Across eight distinct ways of using the macOS on-device Foundation Model
alongside a Claude Code agent, none cost fewer tokens than the agent doing the
work itself. The best configuration found was about 10 percent more
expensive; the typical one, 15 to 25 percent. Every experiment kept the
results correct, so what afmux delivers is the same outcome at roughly the
same cost with the text or the implementation never leaving the machine. That
is a privacy property, not a saving.

The reasons are structural, not implementation gaps:

- A coding agent's spend is dominated by its own turns and the cached prefix
  each turn re-reads, not by text a local model could absorb. Measured on
  Opus 5.5: 76 percent of cost is cache writes, an extra turn costs about
  $0.01, loading a skill about $0.045.
- Frontier agents do not read large output raw. In 60 headless runs, Opus and
  Sonnet grepped, headed and tailed; Claude Code also truncates Bash output
  at 30k characters. The saving that offloading targets is mostly already
  taken.
- The on-device model (3B class) transcribes what it is told line by line and
  fails anything it must work out: counting, diff reading, calendar
  arithmetic, argparse wiring, and any output over about 100 lines. A spec it
  passes is as long as the code; a spec short enough to save tokens is a
  spec it fails. It is also deterministic with no temperature control, so
  retries and sampling, the levers that make small-model protocols work in
  the literature, are unavailable.

## Method

All agent-side numbers come from the harness, not self-reports: `claude -p`
with `--output-format stream-json` for cost and token fields, and the Agent
tool's reported `subagent_tokens` for field tests. Controls were run with
identical prompts in fresh directories. The on-device model was driven
through `/usr/bin/fm` on macOS 27.0.1, arm64. Correctness was graded against
known answers or hidden unit tests. Where a claim depended on `fm`
behaviour, it was probed directly before being relied on.

## Facts about `fm` (measured)

| fact | value |
|---|---|
| context window | 8192 tokens, instructions plus prompt plus output; an 8009-token prompt works, 8209 fails |
| inputs over ~15k tokens | misreported as a guardrail refusal |
| concurrency | concurrent calls queue on the device; none fail |
| killing the client | frees the model immediately |
| sampling | nearly deterministic without `--greedy`; no temperature or seed flag |
| schemas | `fm schema`-shaped JSON with `x-order` is required; `enum` is enforced by constrained decoding |
| guardrails | `permissive-content-transformations` rescued a refused plain-text log summary; it did not rescue a refused schema extraction |
| agent sandbox | `fm respond` and `fm count-tokens` fail with ModelManager error 1008; `fm available` passes |
| speed | 1 to 5 s per short answer; 20 to 48 s for a 70-line module; about 2 s per 600-token read chunk |

## 1. Pipe mode: summarise, classify, extract piped output

Design: a skill plus `afm` CLI; the agent pipes command output into a preset
and reads a short answer. Three benchmark rounds, Opus, seven fixture tasks
(four meant to trigger, three not), with versus without the skill.

| round | inputs | cost with vs without (should-trigger tasks) | afm answered | right |
|---|---|---|---|---|
| 1 | 16k to 62k tokens | +14% Opus | 0 of 4 (exit 6, over budget) | n/a |
| 2 | 1.7k to 6.9k tokens | +15% Opus, flat Sonnet | 4 of 4 | 1 of 4 |
| hook | round 2 inputs, PostToolUse hook rewrites Bash output, no skill | off $0.490, truncate-only $0.498, fm digest $0.491 | hook fired 3 times | all right, same as truncation |

Round 2 answers: the test digest was right; the log summary said three of
four workers timed out when all four did; the build extract counted 13
warnings against 10; the commit message ignored a 176-line file. The agents
caught every wrong answer with grep, which is why cost rose. Wall time was 2
to 5 times worse. Under the owner's real strict sandbox the skill was a pure
tax: exit 5, no retry possible.

Five research agents then reviewed the design. Their findings, each checked:

- Behaviour: triggering worked; the agent's refusals of `--chunk` were correct.
- Cost model: reconstruction of every reported cost from token counts to the
  cent at the 1-hour cache-write rate; break-even for a skill-loaded
  delegation needs 5,000 tokens kept out of context, and afm's ceiling is 7k.
- Capability, 31 probes: the model cannot count, cannot read unified diffs
  (pre-parsing into added and removed lines fixed it), and confabulates one
  detail per summary; it is reliable on yes-or-no, closed labels, co-located
  item names and single fields after grep pre-filtering.
- Architecture: a PostToolUse hook can replace Bash output before the model
  sees it, outside the sandbox, at zero extra turns (verified).
- Skeptic: Haiku does the same jobs for under a cent; the only edge is
  privacy.

The hook experiment above tested the architecture recommendation and showed
nothing left to save.

## 2. Implementer: the agent writes specs and tests, the model writes code

Pivot: `afm run steps/` executes test-gated step files on the model, retries
with the failing output, rolls back on failure, and reports once.

### Single-function benchmark (harness, no agent)

Seven specs with hidden tests, one retry:

| implementer | tasks fully passed | tests | cost |
|---|---|---|---|
| on-device via `fm` | 4 of 7 (3 of 7 through `afm`; wording-sensitive) | 37 of 48 | $0 |
| Haiku 5.5 | 7 of 7 | 48 of 48 | $0.010 |
| Sonnet 5.5 | 7 of 7 | 48 of 48 | $0.037 |

### Field tests: five Opus agents build modules through afmux versus five by hand

Same five tasks each round (INI parser, log analyser, text utilities, date
arithmetic without `datetime`, a four-module CSV CLI). Controls were stable
across rounds, 35.3k to 38.1k tokens per task.

| round | step shape and spec style | tokens vs by hand | wall vs by hand | first-try steps | modules the agent wrote itself |
|---|---|---|---|---|---|
| 1 | one function per step, loose guidance | +26% | 7x | 15 of 24 | 1 |
| 2 | one function per step, pseudocode | +20% | 4.7x | 20 of 25 | 1 |
| 3 | one module per step, pseudocode | +10% | 2.1x | 7 of 8 | 0 |
| 4 | one module per step, plain English | +14% | 3.7x | 3 of 8 | 5 |
| boilerplate | argparse CLI and six record classes from tables | +13% and +16% | 6 to 9x | 0 of 8 attempts | all |

Round 3 is the best configuration measured. All five agents in it reported
that the spec they wrote was as long as the code, and one produced a 70-line
spec for a 70-line module. Round 4 removed that by requiring plain-English
specs; the model then failed five of eight modules and the agents wrote them,
so the cost rose again. The boilerplate round tested the last hypothesis,
that a short tabular spec might yield a long module: specs were a third to an
eighth of the code and the model produced nothing usable in eight attempts
(syntax errors, spec prose pasted into code, a module importing itself, two
timeouts on 250-line output), while Opus wrote the same modules in 74 to 119
lines by factoring the repetition out.

Retries never changed the outcome in rounds 3 and 4: every retry produced
byte-identical code, and switching retries to non-greedy decoding made no
difference because `fm` has no usable randomness.

Per-round fixes driven by the agents' reports: skip steps whose tests
already pass, allow context files produced by earlier steps, regression
checks after each step, richer failure notes, stale bytecode cleanup, header
comment parsing, zero-test warnings, a summary line. Fifteen pull requests in
all, 83 unit tests against a fake `fm`.

## 3. Post-hoc review and test writing

Five hand-written, passing modules, three with one planted one-token bug.

| role | result |
|---|---|
| reviewer, plain English | 0 of 3 bugs found; yes-or-no gate said "no" on all 8 files; 2 false reports on correct code |
| test writer from the code | one module: no runnable tests; one: 27 tests with 7 wrong and the bug uncaught; one: timed out at 180 s |

A review the agent must read and refute costs more than no review.

## 4. Read mode: MinionS-style question answering over a long file

Borrowed from HazyResearch's MinionS (5.7x cloud-cost reduction at 97.9
percent accuracy with an 8B local model, on documents the cloud would
otherwise read whole). `afm read FILE --ask Q` chunks the file (600 tokens;
1500 missed a decisive sentence), asks per chunk for a verbatim quote or an
abstention, drops quotes not in the chunk, and prints survivors with line
ranges. No free-text answer field: measured, the model's answers overreached
beyond their quotes.

A 1,060-line, 23.5k-token documentation page, five questions, Opus, five runs
per arm:

| arm | mean cost | range | wall | correct |
|---|---|---|---|---|
| no afmux (`cat -n`, truncated by Claude Code, then grep) | $0.198 | 0.177 to 0.256 | 17 to 50 s | 25 of 25 |
| `afm read` | $0.205 | 0.161 to 0.219 | 154 to 521 s | 25 of 25 |

A wash. The baseline never paid for the whole document, and the agent grepped
afterwards for exact line numbers. The paper's sampling lever is closed by
`fm`'s determinism.

## 5. Where the agent's tokens actually go

From 631 local session transcripts: subagents produce more than twice the
main conversation's assistant messages, and 98.5 percent of subagent messages
run on Opus or Fable. Haiku handled 1.5 percent, almost all from the built-in
`claude-code-guide` agent. Claude Code does no automatic routing of user work
to a small model; Explore, Plan and general-purpose subagents inherit the
session model. Putting Explore on Haiku or forcing subagents onto Sonnet
would touch the majority of this user's token volume, which no local-model
scheme can.

## What would change the answer

- A local model that can be sampled, or an engine that exposes temperature
  (the FoundationModels framework does; the `fm` CLI does not).
- A stronger local model: the MinionS paper's 8B recovers 98 percent of
  cloud accuracy on extraction, the 3B class 93 percent, and neither was
  tested on code generation.
- A workload where the agent genuinely reads long prose whole, rather than
  structured files it can grep.

## What exists at the end

A tested, documented tool with two modes, `afm run` and `afm read`, an
installer, a 59-line skill, and a spec that records every measurement above.
It works. It is not cheaper than not using it.
